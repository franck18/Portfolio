Avant de commencer

Le besoin et mon rôle

Le besoin

Une image qui se construit correctement n'est pas forcément sûre. Il fallait créer une chaîne capable d'arrêter la livraison si le code, la configuration ou les dépendances présentent un risque élevé, puis prouver que le conteneur déployé conserve les protections attendues.

Mon rôle

J'ai développé l'API et ses tests, écrit la chaîne locale et le workflow GitHub Actions, épinglé les dépendances de build, configuré les scans et le SBOM, puis durci et contrôlé le conteneur déployé.

Fonctionner sur une VM limitée à 2 vCPU et environ 4 Go de RAM.
Bloquer toute vulnérabilité HIGH ou CRITICAL détectée par le scanner.
Éviter root, les capacités Linux inutiles et l'écriture sur le système de fichiers principal.
Réduire le risque de remplacement d'un tag dans les dépendances de la pipeline.
02

Pourquoi cette méthode

La solution choisie

Des quality gates locaux reproduits dans GitHub Actions

Le script local donne une preuve exécutable avant publication, tandis que le workflow GitHub prépare la même logique pour l'intégration continue. Les images et actions externes sont épinglées par digest ou SHA complet afin que la pipeline exécute exactement les composants contrôlés.

Une API HTTP Python standard expose un healthcheck et une route d'information.
Quatre tests unitaires contrôlent les routes et les en-têtes de sécurité.
Trivy analyse le dépôt, les secrets, le Dockerfile et l'image construite.
Le build utilise une image Python Alpine épinglée par digest SHA-256.
Un SBOM CycloneDX inventorie les composants de l'image.
Docker Compose déploie le service sur 127.0.0.1 avec des protections de runtime.
GitHub Actions prépare la publication immuable dans GHCR après validation.

04

Contrôler le fonctionnement

Comment j’ai vérifié

Tests réalisés

  • Compilation statique puis exécution de quatre tests unitaires.
  • Recherche de secrets et de mauvaises configurations dans le dépôt.
  • Scan bloquant HIGH/CRITICAL de l'image Docker finale.
  • Smoke test HTTP et contrôle des en-têtes de sécurité.
  • Inspection du runtime et observation du healthcheck sur plusieurs cycles.

Résultats observés

  • Les huit étapes de la pipeline locale se terminent avec succès.
  • Les quatre tests unitaires passent et l'API répond avec les en-têtes attendus.
  • Trivy affiche 0 vulnérabilité pour les composants détectés dans l'image.
  • Le conteneur utilise l'UID 10001, un rootfs en lecture seule et aucune capacité Linux.
  • Le service reste healthy avec environ 12 Mo de RAM au repos.
05

Prendre du recul

Limites et améliorations

Sécurité et utilisation

  • Actions GitHub épinglées par SHA complet et images externes par digest.
  • Utilisateur non-root, `no-new-privileges` et toutes les capacités supprimées.
  • Limites de 128 Mo, 0,25 CPU et 64 processus.
  • Service accessible uniquement sur l'interface locale de la VM.
  • En-têtes CSP, X-Frame-Options, nosniff, no-referrer et no-store.

Ce que j’améliorerais

  • La publication GHCR et le déploiement distant nécessitent encore un dépôt GitHub et des environnements configurés.
  • Le laboratoire ne mesure pas la charge, la latence ou la montée en charge de l'API.
  • Le secret scanning local complète les contrôles mais ne remplace pas une solution centralisée avec historique.
