01

Avant de commencer

Le besoin et mon rôle

Le besoin

Un réseau plat permet à une machine compromise d'atteindre trop facilement les ressources internes. Il fallait démontrer une segmentation avec une DMZ, des flux strictement nécessaires, des blocages observables et une preuve réseau exploitable.

Mon rôle

J'ai conçu le plan d'adressage, créé les network namespaces et les liaisons veth, écrit la politique nftables, automatisé les cinq tests de flux et capturé une session HTTP avec tcpdump.

Tout simuler dans une seule VM sans ajouter de machine virtuelle.
Forcer chaque communication inter-zone à traverser le pare-feu Linux.
Ne pas modifier le réseau VMware ni le pare-feu principal de la VM.
Nettoyer uniquement les ressources créées par le laboratoire.
02

Pourquoi cette méthode

La solution choisie

Quatre network namespaces et une politique default deny

Les namespaces offrent de vrais espaces réseau isolés sans coût mémoire important. Trois paires veth imposent le passage par le namespace pare-feu. La chaîne forward nftables utilise une politique DROP et n'accepte que les flux décrits dans le besoin.

La zone externe 10.10.10.0/24 simule un réseau non fiable.
Le namespace pare-feu possède une interface dans chaque sous-réseau.
La DMZ 172.16.10.0/24 héberge un service web sur TCP/8080.
Le LAN 192.168.50.0/24 représente le réseau interne protégé.
Le routage IPv4 est activé uniquement dans le namespace pare-feu.
Les règles stateful acceptent les réponses established/related et comptent chaque politique.
tcpdump conserve un fichier PCAP du flux HTTP autorisé.

04

Contrôler le fonctionnement

Comment j’ai vérifié

Tests réalisés

  • Test du LAN vers le service web de la DMZ sur TCP/8080.
  • Test de la zone externe vers le service DMZ publié.
  • Test ICMP de diagnostic du LAN vers la zone externe.
  • Tentatives externes et DMZ vers le LAN, attendues comme bloquées.
  • Lecture des compteurs nftables et de la capture tcpdump.

Résultats observés

  • Les cinq scénarios de segmentation réussissent.
  • La zone externe atteint le service publié sans atteindre le LAN.
  • La DMZ ne peut pas initier de connexion vers le LAN protégé.
  • Le compteur default deny augmente lors des tentatives interdites.
  • Le PCAP montre la négociation TCP puis la requête HTTP GET vers la DMZ.
05

Prendre du recul

Limites et améliorations

Sécurité et utilisation

  • Politique de transfert DROP avant l'ajout des exceptions nécessaires.
  • Suivi d'état pour limiter les retours aux connexions établies ou associées.
  • Aucune route directe entre les zones ne contourne le pare-feu.
  • Scripts limités aux namespaces préfixés `pnet-` pour protéger l'hôte.
  • Scan des secrets, syntaxe Bash et validation nftables automatisés.

Ce que j’améliorerais

  • Le laboratoire ne couvre que l'IPv4 et un unique service web en DMZ.
  • La haute disponibilité du pare-feu, le NAT Internet réel et les VPN sont hors périmètre.
  • Les namespaces simulent les zones mais ne remplacent pas une validation sur des équipements physiques.
