Before starting

The need and my role

The need

An image that builds successfully is not necessarily secure. I needed a delivery chain that stops when code, configuration or dependencies present a high risk, then proves that the deployed container retains the expected protections.

My role

I developed the API and tests, wrote the local chain and GitHub Actions workflow, pinned build dependencies, configured the scans and SBOM, then hardened and inspected the deployed container.

Run on a VM limited to 2 vCPU and approximately 4 GB of RAM.
Block any HIGH or CRITICAL vulnerability found by the scanner.
Avoid root, unnecessary Linux capabilities and writes to the main filesystem.
Reduce the risk of tag replacement in pipeline dependencies.
02

Why I chose this approach

The chosen solution

Local quality gates reproduced in GitHub Actions

The local script provides executable evidence before publication, while the GitHub workflow prepares the same logic for continuous integration. External images and actions are pinned by digest or full SHA so the pipeline runs exactly the reviewed components.

A standard-library Python HTTP API exposes a health endpoint and an information route.
Four unit tests check routes and security headers.
Trivy scans the repository, secrets, Dockerfile and built image.
The build uses a Python Alpine image pinned by SHA-256 digest.
A CycloneDX SBOM inventories the image components.
Docker Compose deploys the service on 127.0.0.1 with runtime protections.
GitHub Actions prepares immutable publication to GHCR after validation.

05

Looking back

Limits and improvements

Security and operation

  • GitHub Actions are pinned by full SHA and external images by digest.
  • The runtime is non-root with `no-new-privileges` and all capabilities removed.
  • Limits are set to 128 MB, 0.25 CPU and 64 processes.
  • The service is reachable only from the VM's loopback interface.
  • CSP, X-Frame-Options, nosniff, no-referrer and no-store headers are set.

What I would improve

  • GHCR publication and remote deployment still require a GitHub repository and configured environments.
  • The laboratory does not measure API load, latency or scalability.
  • Local secret scanning supports the controls but does not replace a central service with history.
