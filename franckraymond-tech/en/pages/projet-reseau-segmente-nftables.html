01

Before starting

The need and my role

The need

A flat network lets a compromised machine reach too many internal resources. I needed to demonstrate segmentation with a DMZ, strictly required traffic, observable blocking and reusable packet-level evidence.

My role

I designed the addressing plan, created the network namespaces and veth links, wrote the nftables policy, automated five traffic tests and captured an HTTP session with tcpdump.

Simulate the complete topology in one VM without adding another virtual machine.
Force every inter-zone communication through the Linux firewall.
Do not modify the VMware network or the VM's main firewall.
Remove only the resources created by the laboratory.
02

Why I chose this approach

The chosen solution

Four network namespaces and a default-deny policy

Namespaces provide real isolated network stacks with a small memory footprint. Three veth pairs force traffic through the firewall namespace. The nftables forward chain uses a DROP policy and accepts only the flows stated in the requirements.

The 10.10.10.0/24 external zone simulates an untrusted network.
The firewall namespace has one interface in each subnet.
The 172.16.10.0/24 DMZ hosts a web service on TCP/8080.
The 192.168.50.0/24 LAN represents the protected internal network.
IPv4 forwarding is enabled only inside the firewall namespace.
Stateful rules allow established and related replies and count every policy.
tcpdump retains a PCAP file for the permitted HTTP flow.

04

Checking that it works

How I checked my work

Tests performed

  • Tested LAN access to the DMZ web service on TCP/8080.
  • Tested the external zone against the published DMZ service.
  • Tested diagnostic ICMP traffic from the LAN to the external zone.
  • Attempted external and DMZ access to the LAN, which had to be blocked.
  • Read the nftables counters and tcpdump capture.

Observed results

  • All five segmentation scenarios pass.
  • The external zone reaches the published service without reaching the LAN.
  • The DMZ cannot initiate a connection to the protected LAN.
  • The default-deny counter increases during forbidden attempts.
  • The PCAP shows the TCP handshake followed by the HTTP GET request to the DMZ.
05

Looking back

Limits and improvements

Security and operation

  • The forward chain uses a DROP policy before required exceptions are added.
  • Connection tracking limits return traffic to established or related flows.
  • No direct route between zones bypasses the firewall.
  • Scripts target only namespaces prefixed with `pnet-` to protect the host.
  • Secret scanning, Bash syntax and nftables validation are automated.

What I would improve

  • The laboratory covers IPv4 and one web service in the DMZ.
  • Firewall high availability, real Internet NAT and VPNs are outside scope.
  • Namespaces simulate the zones but do not replace checks on physical equipment.
