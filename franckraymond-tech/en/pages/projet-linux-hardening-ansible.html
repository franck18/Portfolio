01

Before starting

The need and my role

The need

An overly permissive Linux installation may allow direct root SSH access, passwords and unnecessary features. I needed to demonstrate realistic, repeatable and measurable hardening without risking access to the main VM.

My role

I designed the Ansible role, isolated the target in a locally accessible Rocky Linux container, automated the SSH, sudo, sysctl and auditd measures, then wrote the verification playbook and security scans.

Never modify the SSH service used to administer the host VM.
Use key authentication without publishing any private key.
Keep execution repeatable, with no change during a second run.
Document the exception required by the isolated target's SSH process.
02

Why I chose this approach

The chosen solution

A containerised SSH target managed by Ansible

The VM acts as the controller and manages a separate Rocky Linux target on 127.0.0.1:2222. This allows real system rules and SSH restarts to be tested while keeping the VM's administration access outside the playbook scope.

The Rocky Linux VM runs Ansible as the control node.
A Rocky Linux 9 container provides a deliberately under-hardened SSH target.
A temporary key generated locally bootstraps access for the secops account.
The role manages SSH, sudo, password ageing, sysctl and auditd.
A separate playbook reads the effective configuration and fails if a control is missing.
Trivy scans both the repository and image before evidence is retained.

From plan to practice

What I completed

  1. 01

04

Checking that it works

How I checked my work

Tests performed

  • Compared effective SSH settings before and after hardening.
  • Ran Ansible a second time with `changed=0` and `failed=0`.
  • Checked SSH, the secops account and four protected configuration files.
  • Scanned the Dockerfile, secrets and Rocky Linux image with Trivy.

Observed results

  • The first run applied 12 security changes without failure.
  • The second run confirmed a stable state with 17 successful tasks and no change.
  • Direct root SSH access and password authentication are disabled.
  • The secops account, kernel policies and audit rules are installed.
  • No high or critical vulnerability was detected in the scanned image.
05

Looking back

Limits and improvements

Security and operation

  • The target is published only on 127.0.0.1 and cannot be reached from the VMware network.
  • Private keys and the `.secrets` directory are excluded from published code.
  • Permissions on SSH, sudo and identity files are checked.
  • The Trivy SSH process exception is scoped, dated and documented with compensating controls.

What I would improve

  • The target is a laboratory container rather than a complete production server.
  • SELinux policy design, disk encryption and central identity management are outside scope.
  • The role variables would need adaptation before supporting several Linux distributions.
