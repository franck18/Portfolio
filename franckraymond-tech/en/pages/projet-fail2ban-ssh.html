01

Before starting

The need and my role

The need

Observe the logs produced by an SSH dictionary attack in an authorised environment, then reduce the attack surface and automatically block a source that repeatedly fails authentication.

My role

I built the isolated laboratory, ran the Hydra scenario with test accounts, hardened the SSH service, configured FirewallD and SELinux, created the Fail2Ban jail and collected validation evidence.

Restrict every attack to the laboratory network and test credentials.
Keep administrator access through an SSH key before disabling passwords.
Adapt SELinux and FirewallD to SSH port 15000.
Distinguish slowing attacks from removing the risk of weak authentication.
02

Why I chose this approach

The chosen solution

Layered protection around OpenSSH

Fail2Ban detects repeated failures in logs and temporarily bans the source. It supplements, but does not replace, key authentication, blocked root login, disabled passwords and network filtering. Changing the port mainly reduces noise from automated scans and is not treated as a primary security control.

VM-ATTAQUE uses Hydra only against the authorised target in the isolated network.
VM-DEFENSE hosts OpenSSH on Rocky Linux 9.
sshd records authentication failures used by Fail2Ban.
A custom jail applies a ban after repeated failures.
FirewallD allows the selected SSH port and blocks banned sources.
SELinux associates port 15000 with the expected SSH type.

04

Checking that it works

How I checked my work

Tests performed

  • Checked the effective sshd configuration before restarting.
  • Connected successfully with a key on port 15000 from an authorised source.
  • Checked FirewallD rules and the SELinux port label.
  • Generated repeated failures and checked the Fail2Ban ban.
  • Confirmed that the banned address was refused and read the related logs.

Observed results

  • The test machine address is detected and banned after repeated failures.
  • Connections from the banned source are refused during the test.
  • Key-based access remains operational on port 15000.
  • Root login and SSH password authentication are disabled.
  • The logs provide usable technical evidence of the scenario.
05

Looking back

Limits and improvements

Security and operation

  • The offensive test is strictly limited to an authorised network, target and credentials.
  • Key authentication and blocked root login provide most of the SSH hardening.
  • Fail2Ban slows repeated attempts but does not fix weak credentials or a compromised key.
  • SELinux remains active and the non-standard port is declared with the correct type.

What I would improve

  • The laboratory does not yet measure false positives, the best ban duration or service load.
  • IP-based blocking is less effective against distributed attacks or changing addresses.
  • MFA, a bastion host, VPN and SIEM centralisation are outside the tested scope.
  • The collected logs alone do not amount to a complete forensic investigation.
